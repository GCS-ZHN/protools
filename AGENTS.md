# protools — Agent Notes

`protools4py` is a personal protein-processing Python library
(sequence / structure I/O, annotation, fix/convert, clustering,
AlphaFold/PDB databases, ML dataset splits). One package, no
monorepo. Python `>=3.10` (pinned via `.python-version`).

## Stack & build

- **Package manager**: `uv` only. `uv.lock` is committed. Dev deps
  live in `[dependency-groups].dev` of `pyproject.toml`.
- **Build backend**: `setuptools` + `versioneer` (dynamic version
  from `git tag v*`). `setup.py` is a thin shim; edit it only if
  `pyproject.toml` cannot express the change.
- **Version source**: `protools/_version.py` is generated by
  versioneer — never hand-edit.
- **Two git-source deps** are pinned by commit/tag in `pyproject.toml`
  (`[tool.uv.sources]`): `pdbfixer` (openmm v1.11) and a fork of
  `ProDy` at `GCS-ZHN/ProDy`. Bump these via `pyproject.toml`, not
  by reinstalling ad hoc.
- **No** committed linter / formatter / typechecker / pre-commit
  config. Do not introduce one without explicit user request.

## Install / verify

```bash
uv sync --locked --all-extras --dev   # CI command; mirrors .github/workflows/pypi.yaml
uv run pytest                         # full test suite
uv run pytest test/test_seqio.py      # single file
uv run pytest -k renumber              # single case via -k
uv build                              # produces dist/ for PyPI
```

CI also runs `uv run pytest` on every `v*` tag push and publishes
to PyPI via `pypa/gh-action-pypi-publish` (secrets:
`PYPI_API_TOKEN`, `REPO_RELEASE_TOKEN`; var: `PYPI_API_URL`).
Releases are created as drafts.

## Testing conventions

- `pytest` is the only test runner. `.vscode/settings.json` already
  points pytest at `.`.
- Use `tmp_path` for any file output; do not write into `data/`.
- Prefer committed fixtures in `data/` over mocks. PDB/CIF/Fasta
  sources for fixtures must be cited with a real URL and verified
  with webfetch before use.
- Many helpers verify outputs by MD5 against a hard-coded checksum
  (see `test/tools.py::md5_equal`). MD5s in tests must match what
  the current fixture produces — if you change a fixture, recompute
  and update the constant.
- Several tests hit the network (RCSB download, UniProt/ExPASy).
  Treat them as integration tests; failures from 4xx/5xx or rate
  limits are not necessarily code bugs.

## Workflow (effective from today)

- **Plan before coding.** Before touching code, re-familiarize with
  the project architecture by reading
  [`docs/architecture/overview.md`](docs/architecture/overview.md),
  then walk the entrypoints (start from `protools/__init__.py`,
  `seqio`, `pdbio`, `utils.py`, `cluster/`, `database/`,
  `dataset/`, `dock.py` as relevant). Draft a TodoWrite list,
  confirm it with the user, and persist the agreed architecture
  plan as a standalone `*.md` in the repo (e.g.
  `docs/architecture/<topic>.md` or alongside the touched
  module). The doc is the source of truth for what is being built
  this round; update it if scope shifts.
- **Docs move with code.** Every behavior-visible change ships with
  matching updates to:
  - `README.md` — usage / module list / examples.
  - `CHANGELOG.md` — see the convention below.
  If the change does not warrant a doc update, say so explicitly
  and let the user decide.
- **CHANGELOG convention (`CHANGELOG.md`).** One section per
  `git tag v*` release, newest first, e.g.:
  ```
  ## [vX.Y.Z] - YYYY-MM-DD
  ### Added
  - … (#PR)
  ### Changed / Fixed / Removed
  - …
  ```
  - Each entry references the commit(s) / PR(s) that landed it
    using GitHub's standard format, e.g. `(#42)` for a PR and
    `(abcdef1)` for a direct commit. **Do not** paste long
    URLs unless they add value — the short `#42` /
    `abcdef1` form is what GitHub auto-links.
  - Maintain a top section titled `## Development` (above the
    latest released version) that collects every change **not yet
    covered by a `v*` tag**. When a tag is cut, that section's
    entries get moved into the new version section and a fresh
    empty `## Development` is left above it.
  - Subject lines of the change must follow the existing
    convention (look at recent `git log --oneline` to match).

## Hard rules for agents in this repo

- **Protein data is the user's domain.** Sequences/structures, PDB
  IDs, residue numbering, chain IDs, antibody numbering schemes
  (e.g. IMGT/Kabat in `data/ab1218*.a3m`), docking conventions,
  feature annotations — agents routinely hallucinate these. When a
  choice is not pinned by code or a fixture, confirm with the user
  before coding. Cite the source URL and webfetch-verify it.
- **Real data > mocks.** Tests should use real sequences/structures
  sourced from RCSB / UniProt / AlphaFold, not fabricated ones.
  Mock only when a real dependency is unavailable; otherwise prefer
  the real call.
- **Minimal diff.** Touch only what's required for the task. No
  opportunistic refactors, renames, API swaps, formatting sweeps,
  or "while I'm here" edits. Propose them after the main change.
- **Stay in-scope for permissions.** Do not request access to files
  or directories outside this repo unless the task requires it.
  Avoid wildcard permissions. Within the repo, prefer
  `codegraph_explore` / `codegraph_explore` over `find`/`grep`/`cat`.
- **Secrets.** Never stage `.env`, tokens, passwords, or PyPI
  credentials. Do not read `.env` / `**/.env` without explicit user
  approval. CI secrets come from GitHub Actions only.
- **LSP diagnostics are not optional.** Fix every error the LSP
  flags. Suppressing with `# noqa`, `# type: ignore`, or
  `# pylint: disable` requires explicit user approval and must keep
  the suppression to the smallest scope that resolves the issue.
- **No new tooling by default.** Don't add ruff/black/mypy/pre-commit
  unless the user asks. Do not commit dependency-lock churn — if
  you must change deps, edit `pyproject.toml` and let `uv sync`
  regenerate `uv.lock`.
- **Do not commit.** Only commit when the user explicitly asks.
  Release tags (`v*`) trigger the PyPI workflow.
